# 归因：错在哪一步

> 一句话：**不知道错在哪一步，就只能靠感觉改。**
> 这份文档说明怎么把"答错了"归到**最早出错的那一段**，以及当前的数据指到哪里。

## 1. 为什么需要它

检索错了，可能是五种完全不同的原因：

| 看起来像 | 实际可能是 |
|---|---|
| "检索不准" | 语料里根本没有这份文件（S1） |
| "检索不准" | 文件在，但解析出来是空的（S2，扫描件没 OCR） |
| "检索不准" | 文号/日期抽错，索引里挂了错的身份（S3） |
| "检索不准" | 条款切歪了，答案被切到别的条款里（S4） |
| "检索不准" | 条款都在，只是排序错了（S5，真·检索问题） |

如果不分开，改 prompt、调参数都只是在**猜**。所以规则只有一条：

> 从 S1 往后依次检查，**第一个不成立的阶段就是根因**。

## 2. 判定规则

对每道题（带金标文号）按顺序问：

| 阶段 | 判据 | 本项目的检查方式 |
|---|---|---|
| S7 | 题目本身是否有效 | 金标在该年是否已失效 / 题干是否缺主语 |
| S1 | 语料里有没有这份文件 | 金标文号是否在 `data/processed` |
| S2 | 解析出来有没有字 | 该文件 `chars`、`blocks` 是否 > 0 |
| S3 | 身份是否抽对 | 文号、日期是否齐全且非猜 |
| S4 | 条款是否切出来 | 该文件 `clauses` 是否 > 0、路径是否唯一 |
| S5 | 是否取回到（或拒答） | 不过滤排序后，金标是否在 top-50 |
| S6 | 判定是否可用 | 该事项是否有判定器（当前只有落户） |

S5 再拆四类，因为修法完全不同：

- **排序**：金标在候选里，但排第 2–50 名 → 改打分/加权；
- **闸门误拒**：金标在候选里，但被覆盖率闸门拒了 → 改词表/覆盖率口径；
- **召回失败**：金标不在 top-50 → 改召回路径（同义词/向量/文号直查）；
- **误答**：本该拒答（负样本）却答了 → 收紧闸门。

## 3. 当前结果（2026-11-17，dev n=113）

命令：`python -m tools.diagnose.attribute --write`

| 阶段 | 条数 | 占比 |
|---|---|---|
| **S5 检索** | **37** | 33% |
| OK | 76 | 67% |

S5 再拆：**排序 21、闸门误拒 10、召回失败 6**。

另外 8 条不进分母：6 条 `ambiguous`（官方问答脱离上下文，题干缺主语）、
2 条 `stale`（金标在提问年份已失效，是题过期不是系统错）。

**S1–S4 一条都没有** —— 这不是说前四段做得完美，而是说**在这批题上，
语料/解析/抽取/切分没有成为瓶颈**。前四段的缺陷在别的题上才会暴露（比如问
附录里的名单、问 2017 年被下架的文件）。

## 4. 两个真 bug（体检顺手抓到的）

写这套体检脚本的最大收益不是那张表，是**它逼着我对每条链路写一个"存活判据"**，
于是两条静默错误当场暴露：

1. **`(path, sec)` 重复 122 条**：载体模型里每个载体各自切条款，`sec` 都从 0 开始，
   合并后出现两段 `附件/0`。修法：在**合并之后**统一重算 `sec`（`tools/ingest/carriers.py`）。
2. **孤儿从 6 变 206**：一是 `carriers` / `supplements` / `dropped` 里的字节没算作"被引用"；
   二是把 14 个以域名命名的抓取探测样本当成了语料孤儿。修法：补引用来源 + 按文件名识别 `probe`。

两条都不报错，只让数字悄悄变坏。

## 5. 先修哪里（按成本 × 覆盖）

| 顺序 | 修什么 | 条数 | 成本 | 做法 |
|---|---|---|---|---|
| 0 | ~~过期金标~~ | 2 | 已做 | 标 `stale`，不进分母 |
| 1 | **闸门误拒** | 10 | 低 | 补领域词 + 同义词表（"大龄领取失业保险金人员"↔"上述人员"） |
| 2 | **排序** | 21 | 中 | 标题命中加权 + DHR 式文档级分（`doc = max(子块分)`，`final = clause + λ·doc`） |
| 3 | **召回失败** | 6 | 高 | 同义词 → 文号直查 → 向量 → RRF，最后做 |

理由：第 1 项是**改词表**，改完立刻能测；第 2 项要动打分，需要重跑全量评测；
第 3 项是真正难的（召回），放在最后，而且其中一部分可能根本救不回来。

## 6. 怎么验证修对了

每条修复都必须同时给出：

1. 该子类的条数变化（21 → ?）；
2. 整体 `hit@1` 与 95% 区间（不能只看点估计）；
3. **改好/改坏配对**（McNemar），防止"修好 5 条、弄坏 5 条"被平均值掩盖；
4. 写进 `eval/CHANGELOG.md`，注明是在 dev 上调的。

## 7. 面试讲法

> "我们不是笼统说检索不准。我们写了一个归因器，从语料、解析、抽取、切分、检索
> 逐段检查，第一个不成立的阶段就是根因。跑下来 113 条里 76 条正确，37 条卡在
> 检索，再拆开是排序 21、闸门误拒 10、召回 6。所以我们改的顺序是先词表、再打分、
> 最后才动召回——因为它们的成本和可验证性不同。"
