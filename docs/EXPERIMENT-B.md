# 实验 B：现有评测能不能分辨解析质量

> 一句话结论：**不能。** 三个解析器版本在 dev 题上 `hit@1` 完全相同（54%），连 top-1 命中的文档都**一条没变**；而 top-1 条款的文本质量确实在变（伪影 6/83 → 9/83 → 0/83）。这说明我们的评测对"解析得更干净"这件事**零灵敏度**。

## 1. 问题

过去三轮解析修复（v0.3.1→v0.3.2→排除注释节点）都靠**逐份看块**发现和验证，dev 指标一动不动。原因可能有两种：

- **A**：解析质量对检索结果没影响——那就不该再投人力；
- **B**：评测测不出这个维度——那评测本身有盲区，必须补。

这个实验就是为了把 A 和 B 分开。

## 2. 方法

三个版本从 git 取回，其余代码完全相同；每次都**从落盘原件重解析**（不发 HTTP，避免"证据换成今天的证据"），重建索引，跑同一批 dev 题。

| 版本 | git rev | 差异 |
|---|---|---|
| v031 | `6414759^` | 表格逐格重复、正文混 HTML 标签、注释里的 JS 都在 |
| v032 | `6414759` | 表格按行取、剥标签、docx 表格救回、面包屑过滤 |
| v032c | `d9cfda2` | 再排除 HTML 注释节点（93 份文档的 JS 残片归零） |

题目：`eval/questions_v2.json` 的 dev 集（official 100 + version 3 + out_of_scope 18）。
命令：`python -m tools.experiments.parser_versions --run`（约 20 分钟，主要是三次全库重解析）。

## 3. 结果

### 3.1 现有指标

| 版本 | hit@1 | hit@3 | 应答率 | top-1 文档变化 |
|---|---|---|---|---|
| v031 | 54% | 62% | 80% | — |
| v032 | 54% | 62% | 80% | 0 / 100 |
| v032c | 54% | 62% | 80% | 0 / 100 |

配对比较（v031 vs v032c，n=100）：**都对 54，只 v031 对 0，只 v032c 对 0，都错 46**。精确 McNemar 无从算起——**没有任何一条题反转过**。

### 3.2 补一个指标才看得见

对每道已答题取 top-1 条款文本，检查里面有没有"不该出现的字"（`const `/`function(`/`<!--`/`<div`/`当前位置`/`相关稿件`…

| 版本 | 已答 | 含伪影 | 伪影率 | 可定位 |
|---|---|---|---|---|
| v031 | 83 | 6 | 7% | 82 |
| v032 | 83 | 9 | 11% | 82 |
| v032c | 83 | 0 | 0% | 82 |

（v032 比 v031 多，是因为表格改成整行后，某些文档的 top-1 条款落在了原来不同的块上；样本小，只看方向。）

## 4. 顺手抓到的第二个缺陷

把"干净率"固化进 `tools/eval_v2.py` 后，重跑 dev：

```
| official | 100 | 54% | 63% | 0.60 | 80% | 68% | 36% | 92% |
```

**92% 干净 → 8% 的回答带着页尾**：`相关稿件`、`《关于…》`、`打印本页` 被拼进了最后一条条款的正文。全库实测：`打印本页` 160 块、`相关稿件` 67 块，涉及 161 份文档。

修法：`parse.py` 增加 `FOOTER` 正则，**遇到第一个页尾控件就停止收集**（页尾之后全是站点模板）。重解析后：

```
| official | 100 | 54% | 63% | 0.60 | 80% | 68% | 36% | 100% |
```

条款 6,072 → 6,052；`hit@1` 不变，`hit@3` 62%→63%。

**这个顺序很重要**：先有指标，才看得见缺陷。之前三轮修复都没发现它，因为没有任何数字指向它。

## 5. 结论

1. **现有评测对解析质量零灵敏度**：三版 `hit@1` 一模一样，top-1 文档 0 变化。原因是金标是**文号**——只要命中的文件对，里面那段字是干净的还是带着 JS，指标看不见。
2. **不是解析没影响，是评测问错了问题**。补一个"干净率"立刻从 92% 抓到 100%，并且在修之前就能定位到 161 份文档。
3. **以后解析类改动，判据必须是"干净率 + 引用可定位"，不能只看 hit@1**。否则每次改完都是"看起来提升了"，实际无法验证。

## 6. 这对面试意味着什么

面试官若问"你怎么知道解析改动是有效的"，正确答案不是"hit@1 涨了"，而是：

> 我先证明了现有指标测不出来（三版同分、top-1 零变化），然后补了一个能测出来的量（干净率），用它定位到 8% 的回答带页尾，修完到 100%。**指标的价值在于它能改变哪个决策**，测不出来的指标等于没有。

## 7. 局限

- 只跑 dev split，n=100；version 类只有 3 条，不足以下结论。
- `ARTIFACT` 是正则黑名单，抓不到"语义上不对但字面干净"的问题。
- 伪影率只统计 **top-1**，不覆盖 top-3 与被拒答的题。
- 三个版本的差异是**叠加**的（v032c 含 v032），不能把提升单独归因给某一处修改。

## 8. 下一步：实验 C

现有金标只到"文件级"，所以最多能测到"命中的文件对不对"。要测"引用的那段话能不能支撑结论"，必须做**引用级金标**：

- 抽 30 条已答的 official 题；
- 人工判每一对 `(答案句, 引用条款)` 的关系：`能支撑 / 部分支撑 / 不能支撑 / 引用错文件`；
- 报 `citation precision = 能支撑 / 总数`，并与现在的 `citation_verifiable`（字符包含）对比——如果字符包含 100% 而人工只有 70%，就证明我们那个 100% 是虚高的。

预计半天（30 条 × 2 分钟判 + 汇总）。
