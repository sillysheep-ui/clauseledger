# 三方案对比：D 求职作战台 / G 政策办事 / M 调研尽调

> 数据源均为 2026-11-11 实测 HTTP 码（curl，UA 伪装，跟随跳转）。

---

## D. 求职作战台（原推荐）

**一句话**：JD → 简历证据匹配 → 三态判定（满足/不满足/无证据）→ 缺口 → 人工确认 → 投递记录。
**thesis**：求职 agent 的价值不在替你投更多，而在替你挡住不该投的，并留下"为什么没投"的证据。

**数据**
| 来源 | 状态 |
|---|---|
| `cnamuangtoun/resume-job-description-fit` (HF) | 200，test 1,759 条，三分类，**license 未标** |
| 国家大学生就业服务平台 ncss.cn | 200，职位接口 302 需登录（104.8 万条） |
| BOSS / 实习僧 | 200 但反爬 / 抓取违 ToS → **只做粘贴上传** |

**评测（6 条）**：抽取 F1 / 三态判定混淆矩阵 / 引用可回溯率 / 门控断言（0 次未确认写操作）/ 恢复幂等 pass^3 / 成本上界。

**15 天排期**
D1–3 骨架 + 手写状态机 + JD 抽取｜D4–6 匹配 + 三态 + 首个 eval｜D7–9 门控 + checkpoint + 故障注入｜D10–11 trace + 面板｜D12–13 中文金标 50 条｜D14–15 录屏 + ADR

**死穴**：匹配核心是向量相似，可能被一句"这不就是 embedding"打穿；真实中文 JD 在登录墙后。

## G. 应届生政策与办事助手

**一句话**：落户/补贴/档案/三方/劳动权益问答，每条结论引用政策原文条款，并判定"这条对你不适用"。
**thesis**：政策 agent 的价值不在答得快，在说清**适用条件**和**哪一版**——答错的代价是别人真的去跑一趟。

**数据（实测）**
| 来源 | 状态 | 用途 |
|---|---|---|
| gov.cn/zhengce/ | 200，服务端渲染，列表页可抽 1.7k 字文本 | 国家层面政策 |
| mohrss.gov.cn（人社部） | 200 | 劳动/社保/档案 |
| rsj.sh.gov.cn（上海人社） | 200 | 落户细则 |
| hrss.hangzhou.gov.cn（杭州人社） | 200 | 补贴/落户 |
| beijing.gov.cn/zhengce/ | 200 | 北京政策库 |
| moe.gov.cn / ncss.cn | 200 / 200 | 三方协议、档案转递 |
| 12333.gov.cn | **000 连接失败** | 不可用 |
| gov.cn robots.txt | `Allow: /1` + 一批 Disallow（含 /2016zhengce/ 等），未禁 /zhengce/ | 低频抓取可接受；产品上仍建议"用户贴链接" |

**为什么它的语料特别好**：政策的 ground truth 就是原文本身——不需要标注员判对错，只需要判"这段原文支不支持这个结论"。
**天然的拒答场景**：政策没覆盖（新业态/境外学历/跨省流动）、政策冲突（国家规定 vs 地方细则）、政策过期。

**技术上真正的难点（也是能讲的部分）**
1. **适用条件抽取**：地域 / 毕业年份 / 学历 / 社保月数 / 单位性质 五维结构化，答之前先判"你是否满足前提"。
2. **版本管理**：同一事项 2024 版和 2026 版不同，必须按生效日期选版本，且在答案里标注"依据 X 年版"。
3. **条款级引用**：答案要落到"第 X 条第 Y 款"，不是整篇文档。
4. **跨文档冲突**：地方细则与国家规定不一致时，标冲突而不是选一个。

**评测（6 条）**
1. 引用可回溯率（结论 → 条款，人工抽检 50 条）
2. **适用条件判定混淆矩阵**（适用/不适用/不确定，重点看"不确定"被误判成"适用"）
3. 版本正确率（问 2026 届，是否引 2026 版）
4. 拒答率（30 条超范围问题）
5. 冲突标注率（构造 10 组冲突）
6. 恢复幂等（批量导入政策中断续跑）

**15 天排期**
D1–2 三城政策抓取 + 版本落库｜D3–4 条款级切分 + 引用定位｜D5–6 五维适用条件抽取｜D7–9 检索 + 生成 + 拒答｜D10–11 门控（不确定→给办理指引而非结论）｜D12–13 金标 30 条｜D14–15 录屏 + ADR

**死穴**：**金标成本最高**。你要读懂政策才能标 30 条，保守估计 12–15 小时纯阅读；而且是"读得慢就做不完"的硬约束。

## M. 调研 / 尽调 agent

**一句话**：给一个选型问题，自己规划查什么、读 N 个来源，产出对比表，**每一格都带可点开的来源**，查不到就标"未验证"。
**thesis**：调研 agent 的价值不在写得长，在每条结论都能点开——无来源的断言数是 0。

**数据**：无需自建语料，来源即互联网。但需要**来源登记表**（URL、抓取时间、内容 hash、HTTP 码），否则无法复验。

**评测（5 条，最干净的一组）**
1. **来源可达率**：报告里所有引用 URL 复验 HTTP 200（全自动，零人工）
2. **内容 hash 一致率**：抓取时 hash vs 复验时 hash，检测来源被改/被删
3. **断言-来源对齐率**：抽 50 条断言，判"引用页是否真的支持这句话"（半自动）
4. **无来源断言数**：必须为 0（全自动）
5. **未验证标注诚实度**：它标"未验证"的格子，实际是否真的查不到（全自动抽检）

**技术上真正的难点**
1. 长任务规划（查哪个站、查几个、何时停止）
2. 上下文管理（读 20 个页面，token 会炸——正好对应面试第 8 题）
3. 冲突检测（star 数两个来源不一致时怎么办）
4. 中断恢复（读到第 12 个源时崩了）

**15 天排期**
D1–2 来源登记 + 抓取器｜D3–4 断言抽取 + 引用对齐｜D5–6 复验器（Hash/HTTP）｜D7–9 多源冲突 + 拒答｜D10–11 报告生成 + trace｜D12–13 50 条断言标注｜D14–15 录屏

**死穴**：产品形态撞 deep research（OpenAI/Gemini 已做），且"调研质量"本身难评——只能评"可追溯"，评不了"有没有洞察"。

## 三方对比

| 维度 | D 求职 | G 政策 | M 调研 |
|---|---|---|---|
| 失败模式产量 | 3.5 | **4** | 3.5 |
| 评测锚点强度 | **4.5** | 4 | 3.5 |
| **金标制作成本**（越低越好） | **低**（JD 要求短，标得快） | 高（读政策 12–15h） | 中 |
| 自用频率 | **5** | 3.5 | 4.5 |
| 拥挤度（越低越好） | 3 | **4.5** | 3 |
| 2 周可做完 | **4** | 3 | 3.5 |
| 演示画面 | 中 | 中 | **好**（"我让它调研了 agent 框架"） |
| 讲故事的锋利度 | 中 | **高** | 高 |
| 面试官第一反应 | "求职工具？" | "政策问答会不会答错" | "这不就是 deep research" |

**排序：D ≈ G > M**

- **D** 赢在"你每天真的用"，输在故事不够锋利。
- **G** 赢在"审计优先"讲得最漂亮（适用条件 + 版本 + 冲突 + 拒答，四项全是你的主线），输在金标要你自己读政策，且你只在这半年用得上。
- **M** 赢在贴合当下、评测最自动化（可点开 = 机器能验），输在撞品类。

---

## 我的建议

**如果只看"面试讲得漂亮"：G。**
**如果看"综合最不容易翻车"：D。**
**如果看"你现在最需要、且能立刻长数据"：M。**

三条路的分水岭只有一个问题：**你愿不愿意花 12 小时读政策文件？**
- 愿意 → G，它的"适用条件判定"是你所有主线里最能讲的一个设计。
- 不愿意 → D（省时间）或 M（省标注）。

**不建议混合。** 三个方向各做一半，等于三个都没做透——这正是面试官说的"十个有八个长得一模一样"的那种项目。
