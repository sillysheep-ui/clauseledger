## 0. 一句话结论

**做「求职作战台」窄版：JD → 简历证据匹配 → 三态判定（满足/不满足/无证据）→ 缺口 → 人工确认 → 投递记录。**
主张（thesis）：**求职 agent 的价值不在替你投更多，而在替你挡住不该投的，并留下"为什么没投"的证据。**
v2 再加"协议体检"（三方/劳动/租房合同），把第二个不可逆动作（签字）也纳入门控。

## 1. 我撤回了之前的推荐

上一轮我推荐**招投标合规审查**，理由是"政采 PDF 公开可下 + 废标条款是内生 ground truth"。
实测后撤回：数据维度 2.0/5（ccgp 403、全文多需注册付费）、自用频率 1/5（应届生不会投标）、工期 2/5（长文档+领域知识，10–15 天只能做浅层规则版）。**综合 2.0，六场景垫底。**

教训记下来：**"数据公开可下"不等于"数据可用于评测"**——能下到公告 PDF，不等于能下到带标注的判定标准。

## 2. 筛选标准要换（这是本轮最重要的判断）

之前的五维打分（数据/评测/日活/演示/工期）漏了一条，而这条恰好是面经证据指向的核心：

> 15 道面试原题里至少 5 道是**失败模式题**：重启后怎么恢复、恢复后怎么保证一致性、路径震荡怎么优化、tool call 参数非法怎么重试、50MB 返回怎么处理、压缩丢信息怎么办。

面试官不考业务，考的是**你的系统在坏的时候长什么样**。所以场景要按"**天然产生多少可讲的失败模式**"来选，而不是按"业务热不热"。

修正后的判据：

| 判据 | 权重 | 说明 |
|---|---|---|
| 失败模式天然产量 | 高 | 长事务 / 写操作 / 高风险 / 多工具 / 长文档，占得越多越好 |
| 可机械评测 | 高 | 有公开标注集，或你能在 3 天内造出 50 条金标 |
| 你能否持续用 | 中高 | 决定 L3（真实失败记录）能不能长出来 |
| 工期 | 中 | 单人 10–15 天 |
| 演示效果 | 低 | 可补拍 |

按这个重算，六场景排序变了：

| 场景 | 失败模式产量 | 评测 | 自用 | 工期 | 结论 |
|---|---|---|---|---|---|
| D 求职投递 | 中（批量长任务/不可逆提交/多步） | 强（英文 1,759 条 + 自标 50 条） | 极强 | 4 | **主选** |
| E 合同审查 | 强（长文档/高风险签字/引用定位） | 强（CUAD 41 类 span） | 弱（一辈子几次） | 3 | **v2 / 备选主选** |
| C 面试陪练 | 弱（无工具无副作用） | 弱（评分主观） | 强 | 4 | 淘汰 |
| A 招投标 | 强 | 弱（无金标） | 极弱 | 2 | 淘汰 |
| B 售后赔付 | 强（写操作/金额） | 中 | 弱 | 3 | 备选 |
| F 制度问答 | 中 | 中 | 无真实语料 | 4 | 淘汰 |

**D 和 E 打平，区别在于：D 给你使用数据，E 给你技术密度。**

## 3. 为什么是 D（而不是 E）

1. **只有 D 能长出 L3。** 未来 3–6 个月你每天在投简历，系统每天有真实输入、真实失败、真实"这个建议我不采纳"。E 一年用两次，攒不出失败案例。
2. **D 的"不可逆动作"天然对应你的主线。** 投递不可撤销、平台有 CD 冷却、投错了归因不了——这正是"什么时候闭嘴"最真实的实例，比任何编造的 prompt 都硬。
3. **D 的评测有外部锚点。** `cnamuangtoun/resume-job-description-fit`（HF，test 1,759 条，三分类 No Fit / Good Fit / Potential Fit）可以直接算 Acc/macro-F1，再叠 50 条中文自标。E 的 CUAD 是**英文商业合同**（并购/许可），和你要签的三方协议不是一回事。
4. **工期可控。** 文本解析比 PDF 页码映射便宜得多——招投标那 4–6 天的 PDF 脏活可以省掉。

**D 最弱的地方（必须承认）**：JD→简历匹配的核心是向量相似度，面试官可能一句"这不就是 embedding 相似"打穿。辩护点只有一个：**我们做的不是打分，是三态判定 + 证据引用 + 缺口**——"无证据"是独立状态，不允许被折叠成"不满足"，更不允许猜成"满足"。这是可评测的（看混淆矩阵的某一格），也是可讲的设计选择。

## 4. 产品形态（窄版，10–15 天）

不做"投递决策"这种大词。做一条闭环：

```
用户粘贴/上传 JD + 简历（本地，不出机器）
  → M1 解析：JD 硬性要求结构化（学历/年限/技能/地点/薪资/截止），每条带原文 span
  → M2 检索：简历里找证据（不是整份打分，是逐条找）
  → M3 判定：满足 / 不满足 / 无证据（三态）
  → M4 缺口：无证据项 → "简历里没有这块，建议补强或放弃"
  → M5 门控：生成建议清单 → 人确认 → 才写入投递记录
  → M6 恢复：批量 30 份 JD 可中断续跑，幂等
  → M7 trace + 评测面板
```

版本节奏：
- **第 1 周**：M0 骨架 + 手写状态机（先不套 LangGraph）+ M1 抽取 + 20 份真实 JD
- **第 2 周**：换 LangGraph（对照 ADR）+ M2/M3 + 50 条中文金标 + 首个 eval 报告
- **第 3 周**：M5 门控 + M6 checkpoint 恢复 + 故障注入
- **第 4 周**：M7 trace + 录屏 + ADR + 投递记录面板
- **v2（可选）**：协议体检

## 5. 面试映射表（这个项目能回答什么）

| 面试原题 | 你项目里的对应物 |
|---|---|
| 工具返回 50MB 炸上下文 | JD 抓取/粘贴的体量上限 + 分段提取 + 超限降级 |
| tool call 格式非法/参数类型错，重试几次 | 结构化输出校验 → 重试上限 → 降级人工，有计数与 trace |
| 服务重启后怎么恢复未完成任务 | 批量 30 份 JD 中途 kill -9，续跑无重复记录（pass^3 报） |
| 恢复后怎么保证一致性 | 幂等键 + 终态断言（DB 记录数 == 期望） |
| 路径震荡怎么优化 | 抽取连续失败 → 熔断 → 换策略，有 trace 证据 |
| 上下文压缩丢信息怎么办 | 多 JD 批处理时的上下文预算，压缩前后关键字段保真率 |
| 评测集怎么构建、多少条、怎么保证覆盖 | 英文公开集 1,759 + 中文自标 50，按难度/行业分层，报 Wilson 区间 |
| 完全交给它为什么不放心 | 门控断言：0 次未经确认的写操作；错误投递率 = 0 |
| 为什么不用 LangChain 自己封装 | ADR：先手写 300 行 loop，再换 LangGraph，对照数据 |
| 上线了吗、日均多少请求 | 自用记录：连续 N 天、处理 M 份 JD（诚实标注样本在自用范围内） |

## 6. 评测设计（吸收 `agent-eval-方案.md`）

六条机械指标，不合成总分：

1. **抽取 F1**：JD 硬性要求字段，英文集 + 中文 50 条
2. **三态判定混淆矩阵**：重点看「无证据」被误判为「满足」的那一格（这是最危险的错误）
3. **引用可回溯率**：每条证据能定位到 JD/简历原文 span
4. **门控断言**：0 次未经人工确认的写操作
5. **恢复幂等**：注入故障 3 次，记录数一致（pass^3）
6. **成本上界**：单份 JD 的 token/步数/耗时上限，超限判失败

报告口径：比例 + 95% Wilson 区间；A/B 用配对比较（McNemar）；失败案例 100% 归类，报频次不报百分比。
`eval_report.md` 第一句写死：**只评测可机械判定的系统行为与事实准确性，不评测内容质量。**

## 7. 风险与最脆弱处

| 风险 | 缓解 |
|---|---|
| 真实中文 JD 在登录墙后，爬取违 ToS | **只做用户主动粘贴/上传**，不爬站；演示时说明这是产品约束不是技术妥协 |
| 简历 PII | 全本地 ollama 处理，不上传；README 明说 |
| "匹配太简单"的质疑 | 三态判定 + 证据引用 + 缺口，不与 embedding 基线比谁分高，比"证据是否成立" |
| 自用数据样本小、有偏 | 明确标注 N，报告 Wilson 区间，不承诺泛化 |
| 美国英文数据集 ≠ 中文 JD | 两套口径分开报，不合并 |

## 8. 需要拍板的一件事

**E（协议体检）要不要进 v1？**
- 不进的代价：项目技术密度略低，"高风险 HITL"只能靠投递这一个门控讲。
- 进的代价：+3–4 天，且要处理 PDF/Word 解析（招投标那 4–6 天的坑会回来一半）。
- 我的默认建议：**不进 v1，放 v2**。理由：先用自用高频把 L3 和评测跑通；协议体检复用同一套 doc→chunk→cite→gate 底座，v2 增量很便宜。

> 若你近期要签三方协议/租房合同，E 的实际价值会立刻上升，那就把它提到 v1 的一个 skill（只做"缺失条款检测 + 引用定位"，不做风险评分）。

## 9. 扩展方向（用户追问"还有其他方向吗"后补搜）

前面的六场景（招投标/售后/面试/投递/合同/制度）是我自己先框定的，漏掉了整个类型。补六个不在框里的：

### G. 应届生政策与办事助手
落户、补贴、档案、三方、劳动权益。**语料是政府公开文件，ground truth 就是政策原文本身。**
- 失败模式：政策有**地域/年份/学历**三重适用条件，答错=害人；必须引用原文条款；不适用时要能说"这条不适用于你"。
- 评测锚点：引用可回溯率、适用条件判定（对应混淆矩阵）、超出语料时拒答率。
- 自用：你自己就是目标用户（落户/三方/档案全要办）。
- 拥挤度：低。死穴：政策更新导致语料过期，需要版本管理（但版本管理本身又是加分项）。

### H. 故障应急（AIOps incident response）
告警 → 定位 → 处置 → 回滚。
- 失败模式：最丰富——长事务、写操作、回滚、权限、多人协作。
- 评测锚点：模拟故障注入后的终态断言、危险动作计数、回滚正确性。
- 自用：0（你不在 on-call）。死穴：没有真实环境，全靠模拟，容易被问"你自己用过吗"。

### K. 编码类窄域（依赖升级 / flaky test 修复 / repo onboarding）
- 失败模式：最丰富（沙箱、执行、回滚、长程任务）。
- 评测锚点：隐藏测试全绿 + 不回归 + diff 最小（SWE-bench 式，最硬的评测）。
- 自用：极高（你天天在写这个项目）。
- 死穴：**极拥挤**（open-code-review 49.8k），且"又一个 coding agent"是 2026 最卷的品类；做窄了才有故事。

### M. 调研/尽调 agent
给一个问题，读 N 个来源，产出带证据的对比表。
- 失败模式：多源长任务、上下文管理、来源冲突、来源失效。
- 评测锚点：**每条结论必须有可点击来源，无来源断言数 = 0**；来源可达率（HTTP 200 复验）；冲突时是否标注。
- 自用：极高（你现在做的就是这个）。
- 死穴：产品层已有 deep research（OpenAI/Gemini），但开源作品里带评测的少；"调研质量"本身难评，只能评可追溯性。

### J. 数据分析 / NL2SQL
- 失败模式：schema linking、SQL 执行错、重试。
- 评测锚点：**最硬的一个**——BIRD/Spider 执行准确率是公开基准，可直接对标。
- 自用：低。死穴：本质是 text-to-SQL，agent 感弱，且是老赛道。

### L. Agent 评测/护栏平台（meta）
- 失败模式：弱（它本身不跑业务）。
- 评测锚点：自证（用它评自己）。
- 自用：中。死穴：抽象，没有业务画面；但可以**作为 D 的副产物**免费获得。

### 统一重排（1–5，越高越好）

| 方向 | 失败模式 | 评测锚点 | 自用 | 低拥挤 | 2 周可做 | 结论 |
|---|---|---|---|---|---|---|
| D 求职作战台 | 3.5 | 4.5 | 5 | 3 | 4 | **推荐** |
| G 政策办事 | 3 | 4 | 3.5 | 4.5 | 4 | 强备选 |
| M 调研尽调 | 3.5 | 3.5 | 4.5 | 3 | 3.5 | 强备选 |
| E 合同审查 | 4.5 | 4 | 1.5 | 4 | 3 | 技术密度备选 |
| K 编码窄域 | 5 | 4.5 | 4 | 1.5 | 2 | 高风险高回报 |
| J NL2SQL | 3 | 5 | 2.5 | 2.5 | 3.5 | 评测最硬但没 agent 感 |
| H AIOps | 5 | 3 | 1 | 4.5 | 2.5 | 讲得好但"没用过" |
| L 评测平台 | 2 | 4 | 2 | 4 | 4 | 当副产物，不当主业 |

**扩展搜索没有改变结论**：D 仍然第一，但 G 和 M 追得很近，且两者都比 D 更像"我自己会天天用"的东西。
真正的分水岭不是方向，而是——**你是否愿意为它做 5 轮失败样本分析**。不做，任何方向都停在 L1。
