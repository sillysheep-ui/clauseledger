# 换召回方式会不会变好

一句话结论：**没有一种换法在 dev 上跑出统计可信的提升。** 稠密向量单独用没有优势（+1pp，噪声，且 hit@3 反而低 9pp）；混合召回与字二元组并列 60.9%，但一个慢 30 倍、一个几乎免费。真正被验证的是另一件事：**当前瓶颈不在"用哪种召回器"，而在词汇对不上**——而字二元组恰好只修这一块。

## 1. 问的问题

> 现在的 hit@1 是 57.6%（线上口径，n=92）。如果换成别的召回方式，会不会明显变好？

四种方式，同一批题、同一份语料、同一套判据：

| 编号 | 召回方式 | 实现 |
|---|---|---|
| A | BM25（现状） | jieba 分词 + `bm25s`，索引建在 6,064 个子块上，按 `pid` 取最高子块分 |
| B | BM25 + 字二元组 | 分词特征之外再叠相邻两字（`丧假` → `丧假` + `丧`+`假` 的二元切片） |
| C | 稠密向量 | `BAAI/bge-small-zh-v1.5`，本地 MPS 推理，余弦相似度 |
| D | 混合（RRF） | A 与 C 的排名倒数融合（k=60），只看名次，规避量纲不可比 |

## 2. 口径（为什么这样比）

- **只换召回，不换后处理**：四种方式都只按自己的分数排序，不加标题加权、不加效力加成；映射到父条款后统一走 `_collapse()` 与 `_prefer_effective()`。这样差异只可能来自召回器。
- **金标判文号**（`tools/eval_v2.py::is_hit`），不是判答案文本。
- **只在 dev 上跑**（n=92，官方问答题，已排除 6 条 ambiguous、2 条 stale）。test/holdout 不动。
- 另跑一行「A+后处理（线上）」作锚点，说明线上 57.6% 里有多少来自后处理而不是召回。

## 3. 结果

| 方法 | hit@1 (95% CI) | hit@3 | MRR | 找到金标 | 平均名次 | 查询延迟(中位) | 建索引 |
|---|---|---|---|---|---|---|---|
| A BM25 | 51/92 = **55.4%** (45–65%) | **78.3%** | 0.678 | 91/92 | 5.82 | 2 ms | 19 s |
| B +字二元组 | 56/92 = **60.9%** (51–70%) | **78.3%** | **0.706** | 89/92 | 5.13 | 2 ms | 10 s |
| C 稠密向量 | 52/92 = **56.5%** (46–66%) | 69.6% | 0.660 | 89/92 | 7.33 | 71 ms | 71 s |
| D 混合 RRF | 56/92 = **60.9%** (51–70%) | 76.1% | 0.699 | 91/92 | 6.63 | 59 ms | 0 s（复用） |
| A+后处理（线上） | 53/92 = 57.6% (47–67%) | 75.0% | 0.670 | 75/92 | — | — | — |

四个 95% 区间**大量重叠**（A 45–65%，B/C/D 46–70%）。只看数字，B 和 D 比 A 高 5.5pp；但区间这么宽，5pp 本身说明不了什么。

## 4. 配对比较（这才是判据）

只看 top-1 对错发生变化的题（McNemar 精确检验，双侧）：

| 对比 | 改好 | 改坏 | p 值 | 结论 |
|---|---|---|---|---|
| A → B | 9 | 4 | **0.267** | 不显著 |
| A → C | 11 | 10 | **1.000** | 纯噪声（几乎对称） |
| A → D | 8 | 3 | **0.227** | 不显著 |

事前定的门槛是「≥6:0（p<0.05）」。三组都没到：B 是 9:4，不是 6:0；C 是 11:10，等于换了个方向抖动；D 是 8:3。

**所以按纪律，一个都不上线。**

## 5. 逐题看：B 到底修了什么

B 改好的 9 题（全部是"问法和条文用词对不上"）：

| 题号 | 问题 | 金标 |
|---|---|---|
| OFFI-049 | 申报**正高级工程师**应符合哪些标准条件？ | 沪人社规〔2018〕21号 |
| OFFI-080 | **工程系列正高级职称**的规范名称是什么？ | 沪人社规〔2018〕21号 |
| OFFI-053 | 哪些人可以申请成为**公益性岗位**安置对象？ | 沪人社规〔2025〕31号 |
| OFFI-067 | 本市**企业划型**工作具体怎样开展？ | 沪人社基〔2020〕77号 |
| OFFI-069/073 | 养老保险**关系转移接续**后的待遇… | 沪人社规〔2019〕29号 |
| OFFI-092 | 按项目参加**工伤保险**的范围和对象？ | 沪人社福发〔2015〕34号 |
| OFFI-054/098 | 培训评价激励 / 灵活就业职业… | 〔2024〕20号 / 〔2023〕25号 |

B 改坏的 4 题里最严重的是 `OFFI-089`（问灵活就业缴费比例，金标〔2024〕3号）从第 1 名掉到**第 48 名**——二元组把"灵活就业"拆出的 `活就`、`业缴` 这类碎片，在别的文件里恰好高频，噪声压过了信号。

**这说明：字二元组不是"更懂中文"，只是把分词边界的错误换成了另一种错误。** 它在"专有名词被切碎"时帮忙，在"碎片碰巧高频"时添乱。

## 6. 成本

| 项 | A | B | C | D |
|---|---|---|---|---|
| 建索引 | 19 s | 10 s | 71 s（一次性编码 6,064 块） | 复用 |
| 索引体积 | 1.4 MB（bm25） | 1.4 MB | +12.4 MB（6064×512 float32） | 两者之和 |
| 查询延迟(中位) | 2 ms | 2 ms | 71 ms | 59 ms |
| 峰值内存增量 | +149 MB | +149 MB | +379 MB | +379 MB |
| 外部依赖 | 无 | 无 | 95 MB 模型 + torch/MPS | 同 C |

结论：**C/D 用 30 倍延迟和 230 MB 内存，换来的 hit@1 与免费的 B 相同**；而且 C 单独用还把 hit@3 拉低 9pp（69.6% vs 78.3%）——向量召回更容易把"整份文件相关但条款不对"的东西排上来。

## 7. 决定

1. **不上线任何一种**。三组配对检验都没过门槛，上线就是拿噪声当收益。
2. **B 记为候选**：零延迟成本、机制清楚（分词边界），如果以后评测集扩到 300+ 条、方向仍然一致，再议。
3. **下一步转向词汇层**（第 4 项），因为这次实验真正证明的是：瓶颈是"问法与条文用词不同"，而不是"打分器不够好"。具体做法按性价比排：
   - 同义词/口语表（生娃→生育、老婆→配偶、赔钱→赔偿）；
   - 条款标题/路径也进索引（现在只索引正文）；
   - 查询改写（把长问句压成"主体 + 动作 + 对象"三个词）。
4. **稠密向量暂不引入**：没有带来增益，却引入模型、缓存、显存/内存与 30 倍延迟；等词汇层做完再评估"混合"是否有边际价值。

## 8. 局限

- **n=92**，只能检测约 10pp 以上的差异；5pp 的增益在这个样本量下注定测不出来。要让 B 这种量级的改动有结论，评测集需要 300 条以上。
- 只比了四种召回器，没有比 reranker（那属于"排序后处理"，与本次问题不同层）。
- 稠密模型只试了一个（`bge-small-zh-v1.5`），没有调 prompt/指令前缀；更大的模型可能更好，但成本也更高。
- 比较时**刻意关掉了标题加权**，所以 A 的绝对数（55.4%）低于线上（57.6%）。这是为了隔离召回器，不是线上真实表现。

## 9. 复现

```bash
# 首次需要模型缓存目录（沙箱不允许写 ~/.cache）
export HF_HOME="$PWD/.hf-cache"

# 单跑某几路
python -m tools.experiments.recall_compare --methods A,B
python -m tools.experiments.recall_compare --methods C,D

# 四路一起跑（含 McNemar）
python -m tools.experiments.recall_compare --methods A,B,C,D
```

结果落在 `eval/reports/recall-<时间戳>.json`：每个方法的逐题名次、汇总、配对检验、峰值内存。

模型：`BAAI/bge-small-zh-v1.5`（约 95 MB），设备 MPS，`sentence-transformers 5.6.0`、`torch 2.12.0`；BM25 用 `bm25s` 默认参数（`k1=1.5, b=0.75`，`method="lucene"`）。
