> 写这份文档的目的不是"再夸一遍方案"，是找出会在演示或面试第 10 分钟崩掉的地方。
> 严重度：🔴 会推翻方案 / 🟠 会在追问时露馅 / 🟡 工程缺陷，改起来便宜

## 0. 结论先行：三个必须先解决的红灯

### 🔴 R1. 这个领域**没有副作用**，所以 HITL 和幂等是空转的

政策咨询是纯读操作：查政策 → 给结论。整条链路上没有任何"做错了会赔钱/发错货"的动作。

后果：
- 我说的"人在环门控"拦的是"输出一段文字"，而不是"提交一个申请"。面试官问「拦下来之后呢？」——答案是"重新生成一段文字"，那就不是门控，是审核。
- 我说的"幂等键 `run_id+step+target_hash`"在只读系统里**没有东西可去重**。ERP-AGENT 的幂等价值在"3 次通过只创建 1 笔订单"，我这里一笔订单都没有。
- 崩溃恢复的价值退化成"省掉重跑 12 次 LLM 调用的钱"。这不假，但撑不起"可恢复状态机"这条主线。

**修复（推荐）**：给流程加一个真实的外部动作，让门控拦的是"会留下痕迹的一步"。

具体做法：结论确认后，agent 调 MCP 工具 `create_apply_task`，往一个本地 mock 的"办事任务系统"写一条待办（材料清单 + 截止日期 + 依据条款）。这个写操作：
- 需要人工批准才执行 → HITL 有了真实对象
- 有幂等键 → 重试不会建两条待办（可演示：杀进程重启，仍然只有 1 条）
- 跨进程、有状态 → 崩溃恢复有了可验证的终态
- 正好是 JD 里点名的 MCP 场景（"MCP 协议、工具调用"）
- 演示时有画面：待办列表真的多了一行

代价：+1.5 天（mock 服务 + 一个 MCP server + 幂等测试）。

替代方案（不推荐）：保持只读，把主线改成"证据审计"，HITL 降级成"用户确认引用是否正确"。诚实但弱，面试官会问"那你和多轮问答有什么区别"。

### 🔴 R2. "规则层是确定性的"这句话是假的

我的叙事是：embedding 只能检索、不懂适用条件，所以加一层规则做确定性判定。

但**规则是谁写的？** 是我从条款正文里用 LLM 抽出来的 DSL。也就是说：

```
条款文本 --(LLM抽取)--> DSL 规则 --(确定性匹配)--> 判定
              ↑ 这一步有错，后面再确定也是错的
```

如果不处理，"确定性"只是把误差从"检索"搬到了"规则抽取"，消融实验 baseline vs full 的对比就不干净——full 变好可能只是因为多了 300 条手写规则，而不是架构更优。

**修复**：
1. 规则抽取本身要有指标：在 50 条金标里挑 100 条条款，人工核对抽出来的 DSL 字段（学历/年限/社保月数/年龄上限），报字段级准确率。目标 ≥0.95。
2. 规则表落库时带 `extracted_by='llm'` + `verified_by='human'` 两个字段，未 verified 的规则**不参与判定**，只做"提示"。这既诚实又可演示（UI 上能看到"3 条规则待核验"）。
3. 在 README 里写清楚：**规则层的确定性只保证"给定规则一定得到同一结论"，不保证"规则一定对"**。这句话本身就是加分项，说明我知道自己在做什么。

### 🔴 R3. 数据形态没验证过，PDF 可能是扫描件

我假设 450 份文档能解析出 4,000–6,000 条条款。但没验过最要命的两件事：
- 政府 PDF 里有多少是**扫描件**（没有文字层）。如果有 30%，就要上 OCR，+3~5 天，且 OCR 错误率会污染引用核验。
- 条件类条款常以**表格**呈现（学历/年限/社保月数），`pdfplumber` 抽出来是散的，表格还原是另一个坑。

**修复**：这是 Day 0 的一小时任务，不是第 3 天的任务。样本取 5 份不同年份、不同区县的 PDF，跑 `pdftotext`，看每页字符数。判据：
- 平均 >500 字/页 → 有文字层，按原计划
- 大量 <50 字/页 → 扫描件，方案要么缩到"只处理有文字层的"，要么加 OCR 并砍掉一个城市

**今天就能验，验完再决定 17 天还是 22 天。**

## 1. 会被面试官问穿的五个点

| # | 追问 | 我现在的答案 | 问题 |
|---|---|---|---|
| Q1 | 「你这个混合检索的词法一路用什么？」 | 我说 RRF 融合向量和 BM25 | **Postgres 没有中文分词**。`pgvector/pgvector` 镜像只带 vector 扩展；默认 `simple` 配置把整句当一个 token，对中文等于没做。这条实际上不存在 |
| Q2 | 「恢复的时候状态存在哪？和 LangGraph 的 checkpoint 是什么关系？」 | 我说 Postgres | 我有**两套状态**：LangGraph checkpoint 表 + 自己的 `runs/steps`。谁是真源？漂移了怎么办？现在答不上来 |
| Q3 | 「Auditor 看不到推理，那它能查出什么？」 | 我说信息隔离 | 它只能查"结论是否被引用条文支持"，查不出"推理跳跃"。这是**能力边界**，必须写在文档里，否则会被当成过度包装 |
| Q4 | 「政策修订了，你怎么知道是同一条？」 | 我说同 URL 内容变就新建版本 | 政府修订**经常换 URL**（新发文替代旧发文）。URL 是来源，不是身份。身份应该是**发文字号**（沪人社规〔2023〕X 号） |
| Q5 | 「你的评测集谁标的？会不会自己出题自己答？」 | 我说 50 条金标 | 如果是我写题、我写答案，就是循环论证。必须有一部分来自**官方 Q&A 问答页**（人社局的"政策解读"就是真实用户问题），另一部分由你人工确认 |

## 2. 我写错的地方（工程缺陷）

| # | 位置 | 错误 | 修法 |
|---|---|---|---|
| E1 | compose `./migrations:/docker-entrypoint-initdb.d` | **只在数据卷为空时执行一次**。第二次改 schema 完全不生效，还不会有任何报错 | 单独迁移命令：`make migrate` 顺序执行 SQL + `schema_migrations` 表记录已应用版本。initdb 目录只放 `CREATE EXTENSION` |
| E2 | api healthcheck `curl -f` | `python:3.12-slim` 里**没有 curl**，容器会一直 unhealthy，`worker` 永远起不来 | 改 `python -c "import urllib.request,sys;sys.exit(0 if urllib.request.urlopen('http://localhost:8000/healthz').status==200 else 1)"` |
| E3 | `arizephoenix/phoenix:latest` | 未锁版本，半年后拉镜像可能起不来 | 锁 `21.0.0` 对应镜像 tag |
| E4 | `001_init.sql` | 缺 `CREATE EXTENSION vector`（以及要用的 `pg_trgm`） | 补 |
| E5 | HNSW + 元数据过滤 | `WHERE city='上海' AND effective_from<=...` 先过滤会**掉召回**（HNSW 是近似图，过滤后可能找不到邻居） | 打开 pgvector ≥0.8 的 `hnsw.iterative_scan = relaxed_order`，或按城市建部分索引 |
| E6 | compose | 没有 `restart: unless-stopped`、没有内存上限（表里写了 512M，yaml 里没落） | 补 `deploy.resources` 或 `mem_limit` |
| E7 | API | 没有任何鉴权，`/v1/ingest` 谁都能打 | 加一个静态 bearer token（单用户够了），同时为 RLS 留 tenant_id |
| E8 | 依赖版本 | 本地 Python 3.13.9 | **镜像锁 3.12**。`arize-phoenix` 要求 ≥3.11，其他库未全部适配 3.13；3.13 的 free-threading 与部分 C 扩展还有坑 |

已核实的版本（2026-11-11 从 PyPI 读）：`arq 0.28.0`（py>=3.9，2026-04 仍发版）、`langgraph 1.2.20`、`langgraph-checkpoint-postgres 3.2.0`、`litellm 1.108.4`（<3.15）、`arize-phoenix 21.0.0`（≥3.11）、`bm25s 0.3.16`、`jieba 0.42.1`（2020 年后没更新，但稳定）。

## 3. 过度设计（建议删）

| 项 | 为什么删 | 保留什么 |
|---|---|---|
| **六级缓存** | 5,000 条条款本地 embedding 几分钟就跑完，缓存省下的不是钱是"几秒"。而 L4/L6 缓存会**让评测看起来比实际稳**——同一问题第二次跑命中缓存，pass^k 直接虚高 | 只留两级：原始文档（避免重复抓站，礼貌问题）、embedding（换解析器时不用重算）。其余删掉 |
| **Langfuse full 档** | 6 个容器、2.5GB、启动 1 分钟。演示时多一个可能起不来的东西 | Phoenix 单容器够了，OTLP 端口一致，以后再加 |
| **11 张表** | `judgements` 可以先存 `runs.payload jsonb`，等真的要按条款聚合再拆表 | 保留 tenants/documents/versions/clauses/ingest_runs/steps/runs/human_gates/corpus_versions/idempotency_keys（10 张） |
| **异构双模型**（云端 advisor + 本地 auditor） | 两个模型都接通的调试成本是 2 倍；异构的证据价值要等评测出来才成立 | 先同模型跑通，标注 `--heterogeneous` 开关，评测阶段再打开做对比 |

## 4. 缺失（必须有）

1. **非目标清单**：README 第一屏写"不做什么"。现在只有"边界：3 城 6 事项"，还不够硬。
2. **失败样本库**：每个失败案例落成一条 fixture，进 `eval/cases/failed/`。这是"L3 有真实失败记录"的唯一证据。
3. **评测运行时间预算**：50 条 × 2 变体 × pass^3 ≈ 300 次 run。本地模型每次 30–60s，就是 3–5 小时——**没人会跑**。硬约束：全套 ≤30 分钟，否则 k 降到 2、或确定性节点全部录制回放。
4. **数据合规声明**：抓取频率（≤1 req/s）、只抓公开文件、标注来源 URL 与抓取时间、免责声明"非法律意见"。写进 README，这是私有化部署作品该有的自觉。
5. **隐私边界**：`profile`（学历/社保/户籍）是敏感个人信息。默认全本地（ollama），云端调用需显式开关，且 UI 上显示"本次请求发往云端"。**这本身就是差异化点**——大多数 agent 作品默认把用户数据发给 OpenAI。
6. **5 分钟演示剧本**：现在还没写。不知道剧本就不知道哪些功能是必须的，容易在第 14 天做了一堆用不上的东西。
7. **每周验收动作**：你复述一遍"这周做了什么、为什么"，讲不顺就是没做对。

## 5. 修订后的方案（diff）

| 项 | 原方案 | 修订 | 影响 |
|---|---|---|---|
| 副作用 | 无 | 加 `create_apply_task` MCP 工具 + mock 任务库 | +1.5 天，HITL/幂等/恢复全部落地 |
| 词法检索 | Postgres BM25（不存在） | 进程内 `jieba + bm25s`，按 corpus_version 落盘 | 持平（更简单，且可解释） |
| 版本身份 | URL | **发文字号 doc_no**，URL 仅作来源 | 持平 |
| 状态真源 | 两套 | checkpoint 是唯一真源，`runs/steps` 是投影（事件写入） | 持平，少一类 bug |
| 规则层 | "确定性判定" | 规则带 verified 标记，未核验只提示；规则抽取单独报准确率 | +1 天（100 条人工核对） |
| 缓存 | 六级 | 两级 | −0.5 天 |
| 文档 | 3 城 × 6 事项 | **先上海 3 事项端到端**，第 8 天再扩 | 风险从"全崩"变成"局部延期" |
| 评测 | 50 条 | 50 条，其中 ≥15 条来自官方 Q&A 页、≥10 条负样本；全套 ≤30 分钟 | +0.5 天 |

**时间线：17 天 → 19 天**（+1.5 副作用，+1 规则核验，−0.5 缓存，+0.5 评测，四舍五入）。如果 R3 验出扫描件，再加 3–5 天或砍掉一个城市。

## 6. 需要你定的三件事

1. **城市与身份**：你关心的是哪 1–2 个城市？你现在是应届/在职/已落户？"3 城 × 6 事项"是我拍的，如果你的真实场景只有"上海 + 应届生落户"，范围应该砍一半，省下的时间放到规则核验上。
2. **副作用这条线要不要加**：加 = 更像系统、能演示幂等和恢复，代价 +1.5 天；不加 = 诚实但弱，主线只能改成"证据审计"。
3. **投递时间**：这个问题从第一天问到现在还没答。它决定要不要砍 v2、要不要把 19 天压到 12 天。**不答我就按"没有硬 deadline，但每周必须有可演示增量"来排**，这是我最不想要的默认值。
