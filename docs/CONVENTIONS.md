# 迭代规范

> 目标不是流程好看，是**三个月后还能看懂自己当初为什么这么改**。

## 分支

- `main` 常绿，任何时点都能演示
- 功能分支 `feat/<短名>`，合并后删除
- 不搞 develop/release 那一套（单人项目，只会增加心智负担）

## 提交信息

```
<type>(<scope>): <一句话，中文，动词开头>

<可选：为什么这么改，不说“做了什么”——做了什么看 diff 就知道>
```

| type | 用途 |
|---|---|
| `feat` | 新能力 |
| `fix` | 修 bug |
| `docs` | 文档 |
| `data` | 语料、金标、fixture |
| `eval` | 评测脚本与报告 |
| `refactor` | 不改行为的重构 |
| `test` | 测试 |
| `chore` | 环境、依赖、配置 |

**scope** 用模块名：`ingest` `parse` `rules` `judge` `graph` `gate` `eval`。

规则：
- 一条提交只做一件事，能单独回滚
- 提交信息里**不写**「优化了一下」「改了点东西」——那等于没写
- 破坏性变更在正文里写 `BREAKING:`
- 每条提交都能通过 `make test`（从 M1 起生效）

## 标签

每次里程碑完成打 tag：`m1-slice` `m2-judge` `m3-system` …
周报需要时打周 tag：`w01` `w02`。

## 决策记录

凡是有「为什么不选另一个」的地方，写 `adr/00N-标题.md`，一页以内：

```
# ADR-00N 标题
## 背景（什么约束逼出了这个决定）
## 选项（至少两个，各自代价）
## 决定
## 后果（接受了什么坏处）
```

已排期的 ADR 选题：

- ADR-001 为什么判定不交给 LLM（有消融数据支撑）
- ADR-002 为什么用四态而不是三态
- ADR-003 为什么多城按能力分级而不是统一支持

## 数据与产物

- `data/raw/` 不入库，可从 `make ingest` 重建
- `data/fixtures/` 入库（小体量，供测试与离线演示）
- 每次 ingest 产出 manifest，记录 git commit、corpus_version、模型 id、金标哈希

## 复盘节奏

每个里程碑结束做三件事：

1. 跑一次全量验收，把数字写进 `docs/eval_report.md`
2. 录 30 秒自述：「这周做了什么、为什么、哪里还不行」
3. 把失败样本进 `eval/cases/failed/`，一条都不能丢
