# 词表：为什么它不该写在代码里

## 1. 问题

原先 `app/retrieval/index.py` 里写死了一张 17 个词的 `USER_WORDS`，`app/retrieval/search.py`
里又各写死了一张 `QUESTION_WORDS`（14 个）和 `WATER`（83 个）。后果：

- 加一个部门、换一批文件、多一个口语说法，都要**改代码 + 改测试 + 重跑评测**；
- 三张表分散在两个文件里，没人知道哪张表在管什么；
- 最要命的是**没人检查这些词有没有用**——词在不在语料里、有没有被切碎，全靠猜。

## 2. 做法：三张表进数据文件，各管一件事

`data/fixtures/lexicon.json`：

| 字段 | 作用 | 用错会怎样 |
|---|---|---|
| `segmentation` | 告诉 jieba"这是一个词，别切开" | 少了 → 词被切碎、检索不到；多了 → 无害但白加 |
| `question_words` | BM25 打分与覆盖率里**不参与** | 不剔 → `怎么`（df=2）idf 7.79，把问答式条款顶到第一 |
| `water` | 覆盖率**分母**里剔除的虚词 | 不剔 → 问得越长覆盖率越低，闸门惩罚"问得具体" |

加载器是 `app/retrieval/lexicon.py`：按 `(路径, mtime)` 缓存，支持 `CLAUSELEDGER_LEXICON`
覆盖，文件缺失时退回空表而不是崩掉。

## 3. 顺手抓到的真 bug：分词依赖调用顺序

`_setup()`（把用户词灌进 jieba）原先只在 `collect()` / `build()` 里调。任何**直接**
`import tokenize` 的调用方——诊断脚本、词表体检、新写的实验——拿到的都是"没加用户词"的分词结果。

第一次跑词表体检时，17 个词里 **11 个显示 df=0**，看起来像"词表白写了"，实际是**体检工具自己拿错了分词器**。

修法：`tokenize()` 内部懒执行 `_setup()`，并且用 `_READY` 只做一次。分词对不对，不该取决于调用顺序。

## 4. 词表体检

```bash
python -m tools.lexicon_check --top 40
```

两条判据，不需要人工猜：

1. `segmentation` 里**一次都没出现**的词 → 白加的（拼错，或语料里没有这个概念）；
2. 出现 ≥20 条、却不在表里的二字以上词 → 可能被 jieba 切碎了，进候选。

修完之后只剩一个真空词：`劳动仲裁`——语料里写的是"劳动争议仲裁"(6) / "劳动人事争议仲裁"(11) /
"仲裁"(21)，四字串一次都没有。已从表里删掉：留着会让人误以为"检索到仲裁"靠的是这个词。

## 5. 现在的结果

```
segmentation 16 个词（原 17，删掉 0 次出现的"劳动仲裁"）
question_words 14
water 82
```

dev 基线不变：official n=92、hit@1 **59%（48–68）**、hit@3 79%、作答率 88%、oos 拒答 100%。

## 6. 还没做

- `question_words` 目前只用于覆盖率和"算分数前的过滤"，**BM25 打分仍包含它们**。下一步要把它们从
  query token 里剔掉（预计能修掉"托育补贴"被引到"注册资金怎么计算"这类假高分）。
- 词表没有版本化迁移：删词会让旧引用对不上，需要时按 `version` 记 changelog。
