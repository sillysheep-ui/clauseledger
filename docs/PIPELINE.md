# 采集与条款化（M1）

> 目标：一份政策文件进来，出去是**可引用的条款**——每条能指回原文的页码与字符位置。

## 技术栈与选型理由

| 环节 | 用什么 | 为什么不用别的 |
|---|---|---|
| 抓取 | `httpx` + 自建限速/重试 | 不需要 Scrapy 的调度器；Playwright 只在 WAF 章节用 |
| 解析 HTML | `bs4 + lxml` | 只要段落序列，不要 DOM 树 |
| 解析 PDF | `pypdf` 逐页 `extract_text` | 不需要版面还原；`page` 是引用定位的第一段 |
| 解析 DOCX | `python-docx` 段落 + 样式 | 保留 heading 才能识别标题层 |
| 去重/版本 | `sha256(原始字节)` | 内容变了才叫新版本，`Last-Modified` 不可信 |
| 条款切分 | 纯正则，四套编号 | **不用 LLM**：切分错了要能复现、能回归 |

## 五个步骤

```
fetch(url)          限速 1 req/s，原始字节按 sha256 落盘（证据，不是缓存）
  ↓
parse(html/pdf/docx) 统一成 Block[index, kind, text, page]
  ↓
metadata            文号/标题/有效期 —— 以列表页为准，正文只作兜底
  ↓
split_clauses       Block → Clause[path, level, text, page, block_index, char_offset]
  ↓
record              写 data/processed/<文号>.json
```

## 三个关键决定

### 1. 文号来自列表页，不从正文猜

第一次跑，三份文件全被判成 `国发〔2021〕7号`——因为正文里第一处「〔〕号」是**引用国务院文件**。
正则没错，位置错了。改成列表页的 `doc_no` 为准，正文提取降级为兜底，并记录 `doc_no_source: list|text`。

### 2. 引用定位用三元组，不用页码

```python
(page, block_index, char_offset) + parser_version
```

PDF 有页码，HTML 没有；只靠页码在 HTML 上无法定位。`parser_version` 是因为偏移量只在同一解析器版本内有效。

### 3. 四套编号体系并存

政策文本没有统一编号：

| 体系 | 样式 | 典型文件 |
|---|---|---|
| 章/节/条 | `第一章` `第一条` | 办法、条例 |
| 汉字顿号 | `一、` | 通知、意见 |
| 括号汉字 | `（一）` | 同一文件的下级 |
| 数字 | `1.` | 再下一级 |

只认「第X条」会在上海文件上得到 **0 条**（实际 29 条）——M0 踩过这个坑。
切分规则：父条款文本包含子条款全文（便于整段检索），引用区间各算各的。

## 实测（上海人社 574 份，解析器 v0.3.2，2026-11-13）

| 指标 | 值 |
|---|---|
| 成功落库 | 574 份（560 份爬取 + 14 份人工补录） |
| 正文字数 | 1,270,528 |
| 条款 | 10,233（中位 8，最大 247） |
| 块 | 33,782 |
| 附件 | pdf 225 / doc 59 / docx 12，解析失败 0（docx 抽 0 字：3 → **0**） |
| 抽取路径 | native 134 / OCR 103 / textutil 59 / unsupported 0 |
| 无编号条款 | 56 份（9.8%），多为表格型延期清单与 1980–2000 年代短通知，正文本身就不分条 |
| 耗时 | 全量重抓 574 份 ≈ 1,700 秒；**从原件重解析 574 份 ≈ 334 秒**（`reparse_all`，不发请求） |

> 语料与解析器版本必须一致：引用偏移 `(page, block_index, char_offset)` 只在同一
> `parser_version` 内有效。混版本 = 自己废掉"可追溯"，所以每次改解析器都全量重建。

单份样本（v0.3.1）：

| 文号 | 字 | 条款 | 备注 |
|---|---|---|---|
| 沪人社规〔2026〕23号 | 5,689 | 74 | 条 36 / （一）38 |
| 沪人社规〔2026〕22号 | 6,737 | 70 | 一、12 / （一）58 |
| 沪人社规〔2019〕42号 | 342 | 3 | 正文在 `<div>` 而不是 `<p>`，靠选择器救回（修前 125 字 / 0 条） |

## 兜底：扫描件与老格式

三轮跑下来，561 份里真正"读不出来"的比例并不低：

| 情况 | 份数 | 处理 |
|---|---|---|
| 扫描件 PDF（无文本层） | 103 | 渲染 + OCR |
| `.doc` 老格式 | 59 | macOS `textutil` |
| docx 表格文字 | 3 份（v0.3.1 全丢） | v0.3.2 起按行抽成 `table` 块（0 字 → 2,184 / 560 / 571 字） |

### 扫描件：渲染 + Apple Vision

判据不是"文件大小"或"页数"，而是**整份 PDF 的中文字符数 < 50 × 页数**。命中后：

```python
img = PdfDocument(path)[i].render(scale=2).to_pil()
res = ocrmac.OCR(img, language_preference=["zh-Hans"]).recognize()
```

**踩坑**：ocrmac 默认语言是英语，中文扫描件会输出 `LENN EN2021 012- 1 -` 这种垃圾。
必须显式传 `language_preference=["zh-Hans"]`，同一页立刻从 20 字垃圾变成 373 字完整正文。

置信度分布 0.71～0.97（中位 0.87），低于 0.5 的块直接丢弃——宁可少，不可错。

### `.doc`：调用系统工具而非装依赖

`.doc` 是 OLE2 二进制，`python-docx` 打不开。没有装 LibreOffice，也不打算为 30 份文件装 700 MB 的套件，
直接用 macOS 自带：

```bash
textutil -convert txt -stdout file.doc
```

### 每条记录都要说明"这份文本是怎么来的"

```json
{"extract": "ocr", "ocr_conf": 0.87}
{"extract": "textutil"}
{"extract": "unsupported"}   // 读不出来就承认
```

**不许假装读到了**：解析失败落 `unsupported`，下游检索跳过、判定给 `unknown`，
而不是给一段空字符串让它冒充"文件很短"。

## v0.3.2：三类"看着没错、其实错"的解析失败

S2 复查时逐份看块，发现的问题都不是崩溃，而是**代码跑通了、内容错了**：

| 缺陷 | 表现 | 根因 | 修法 |
|---|---|---|---|
| 表格被拆成碎片 | 一张表输出成 68 块：先是整表 `table` 块，随后 `序号`/`文件名称`/`文号` 各成一段 | `find_all(..., recursive=True)` 会钻进 `<table>` 的 `<td>` | 手写 DFS，遇到 `<table>` **只取行、不下钻** |
| 正文混入模板源码 | 块文本里出现 `<div class="Xun-tong"><a href=…>` | 页面把模板当文本节点吐出来，lxml 反转义后成了正文 | `_clean()` 剥离残留标签；含 `class=`/`href=` 的块直接丢 |
| 面包屑当正文 | 「您现在的位置：」进了第一个块 | `drop_nav()` 只去重复 ≥3 次的文本，单次面包屑漏网 | 加 `CRUMB` 前缀过滤 |
| docx 表格 0 字 | `沪人社规〔2022〕20号` 三个 docx 附件 chars=0 | `python-docx` 的 `.paragraphs` 不含表格文字 | 按 body 顺序遍历 `p`/`tbl`，表格按行拼 `a \| b \| c` |

效果（574 份全量重解析）：

| 指标 | v0.3.1 | v0.3.2 |
|---|---|---|
| 块 | 34,315 | 33,782 |
| docx 抽 0 字的附件 | 3 | **0** |
| `沪人社规〔2026〕12号` 块数 | 68（含 11 块重复单元格） | 57（表格按行 7 块） |

**没有丢正文**：拿 573 份 HTML 的原页面文本做分母，记录字数/原文字数的中位数是 **1.05**
（附件另算），只有 5 份低于 75%，逐份看过都是导航占比高的短通知。

> 重解析走 `python -m tools.ingest.reparse_all`，从 `data/raw/<sha12>/` 取原件，**不发 HTTP 请求**。
> 为什么不用 `batch.py --force` 重抓：站点随时改版，重抓等于把"证据"换成"今天的证据"，
> 解析器改动的收益就无从比较了。574 份重解析 334 秒，重抓约 1,700 秒。

**一个差点重演的坑**：`reparse` 第一版只把 `bytes` 传给解析器、没传落盘路径，
扫描件 PDF 需要路径才能渲染成图，OCR 静默跳过——103 份扫描件当场变成 0 字，
dev `hit@1` 从 54% 掉到 48%。传路径后回到 54%。**同一类"静默失败"在解析层内部又演了一次。**

### v0.3.14：附录独立成段 + path 不再当主键

- 新增 `APPENDIX`（`附录/附表/附件N`，独立成行且 ≤12 字）→ 提升为 level=1 段，内部按 ≤600 字行块切。
- `Clause` 新增 `sec`（同一 path 的第几次出现）：`path="二、"` 在同一文件可出现 5 次，path 不能当主键。
- 效果：最长条款 17,799→8,646，粘连 11→4，附录条款 0→46，`(path, sec)` 重复 6,293→0。
- 检索无变化（dev hit@1 53%），附录块从未进入 top-1 —— 名单类内容应打 `kind=appendix` 降权（未做）。

## 已知问题

- **静默失败是这套流水线最大的坑**。全量 561 份第一次跑完是「0 失败、8,259 条」，看起来很成功，
  实际上三类文件正文是空的：`.doc` 抛异常被吞成空 `Parsed`、扫描件根本没提取、正文在 `<div>` 里没被 `<p>` 规则命中。
  **程序不报错不等于拿到了内容**——所以每条记录都要带 `stats.chars` 和 `extract`，报告里单独看「0 条款」这一列。
- **正文选择器会圈到侧栏**。加了 `#ivs_content` / `.content` 这类选择器后，20% 的文件反而被截断
  （沪劳资发〔87〕130号：选择器 244 字、实际 537 字）。规则改成：选择器命中后跟"最大文字块"比大小，
  **小于 70% 就判定不可信、退回最大块**。命中错了比没命中更危险，因为它不会报错。
- **同一文件里两套体系**：通知正文用「一、（一）」，附件《办法》用「第X条」，合并后条款层级混排。检索不受影响，但 `path` 语义要小心。
- **无编号条款的短通知**（53 份）目前切出 0 条。后续要么给它们建"整篇即一条"的兜底条款，要么在检索层直接按块返回。
- **OCR 并发会被 Vision 拖死**：5 个进程 × 3 线程同时调 Vision 时，单份 50 页 PDF 从 30 秒劣化到 1 小时
  （实测出现 3,601 秒的记录）。改用全局信号量把并发 OCR 限到 2 份，477 份重建从 2 小时降到 437 秒。
- **加密 PDF**：政务文件常见"打开密码为空"的权限加密，`pypdf` 会抛 `RuntimeError`。
  现在整段 try 包住，失败就转 OCR 渲染（`pypdfium2` 能打开这类文件）。
- **`.doc` 依赖 macOS**：`textutil` 只在 macOS 有。换 Linux 部署要补 `antiword` 或 LibreOffice，属于已知移植成本。
