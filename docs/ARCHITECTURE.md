# ARCHITECTURE.md — 系统全景与环节设计

> 这份文档不排日程，只回答三件事：**系统由哪些环节组成、每个环节的契约是什么、怎么判断它做对了**。
> 具体哪天做什么，等这份定稿后再排。

---

## 0. 一句话与一条主线

**一句话**：输入你的情况，输出"你能办哪条政策、凭什么、还差什么"，每条结论都能点回官方原文的某一句话。

**一条主线**：`检索负责找对文件，规则负责下结论，LLM 只负责解释`。

这三件事一旦混在一起（让 LLM 看着检索结果说"你符合"），整个项目就退化成 RAG 问答——这是本项目唯一不能被越过的高压线。

---

## 1. 全景图

```
        ┌─────────────── 离线：语料建设 ───────────────┐
        │  采集 → 解析 → 条款化 → 规则结构化 → 索引     │
        └───────────────────┬─────────────────────────┘
                            │ corpus_version
        ┌───────────────────▼─────────────────────────┐
        │  在线：一次问答                              │
        │  问题 → 画像 → 澄清 → 路由 → 判定 → 冲突裁决  │
        │      → 门控 → 组装 → 核验 → 动作 → 归档      │
        └───────────────────┬─────────────────────────┘
                            │ run tree
        ┌───────────────────▼─────────────────────────┐
        │  横切：版本 / 审计 / 门控 / 评测              │
        └─────────────────────────────────────────────┘
```

四个横切关注点不属于任何单个环节，但每个环节都必须回答它们：

| 横切 | 在每个环节的问题 |
|---|---|
| 版本 | 这条数据属于哪个 corpus_version？政策改了怎么办？ |
| 审计 | 这一步的输入输出可回放吗？结论能追到源头吗？ |
| 门控 | 这一步出错，谁承担后果？要不要人看一眼？ |
| 评测 | 怎么证明这一步没做错？错在哪一类？ |

## 2. 八个环节的设计

每个环节给四样东西：**契约 / 关键设计 / 失败模式 / 验收**。

### A. 采集与版本（Ingest & Version）

**契约**
```
seed(栏目页) → DocumentVersion{
  doc_id, doc_no(发文字号), title, issuer,
  published_at, issued_at, effective_from, effective_to,
  sha256, raw_path, source_url, attachments[], status
}
```

**关键设计**
- **身份是发文字号，不是 URL**。实测：`沪教委学〔2026〕13号`，印发 2026-04-27、发布 2026-05-06，两个日期都在页面上；2024 年有同名文件 → 同一事项的两个版本，靠文号区分。
- **附件是规则主体，不是补充材料**。实测那份通知正文 17KB、38 行、0 张表格、全文不出现"72"——真正的评分表在《…户籍办法》附件里。抓完正文不抓附件，等于没抓到规则。
- **双日期**：印发日、发布日、生效日三者不同。答案里的"以 X 日状态判定"必须用生效日。
- 限速 ≤1 req/s，记录 robots 与抓取时间；403 的源（实测 gov.cn `/zhengce/zhengceku/`）记成 coverage gap，不静默跳过。

**失败模式**：403 / 附件在另一域名（edu.sh.gov.cn）/ 同名不同年 / URL 变更 / 首页是 JS 壳（实测 firstjob 只返回 464 字节）

**验收**：喂 2024 与 2026 两版同名文件，系统判定为"同一事项的两个版本"而不是两份无关文档；任一文档能答出"它的附件抓到了几个、失败几个"。

---

### B. 解析与条款化（Parse & Clause）

**契约**
```
DocumentVersion → Clause[]{
  clause_id, version_id, path("附件3/二/（一）/1"),
  text, char_start, char_end,
  page, block_index, parser_version,
  kind: 条文|表格|问答|附件清单
}
```

**关键设计**
- **层级栈**：`一、` → `（一）` → `1.` → `①`，遇到更高级编号就回退栈，得到 `path`。有 path 才能说"附件3 第二条第（一）项"。
- **三重定位**：`char_start/end`（原文偏移）+ `page/block_index`（PDF 页内位置）+ `parser_version`。换解析器后偏移会变，所以版本号必须进来，否则历史引用会悄悄指错。
- **表格双存**：原样存 markdown（给人看）+ 抽成 kv（给规则用）。评分表是 `学历→博士 30 分` 这种，kv 才能进 DSL。
- 扫描件识别：`字符数/页数 < 50` 打 `LOW_TEXT` 标记，进 coverage gap，不当正常文档处理。

**失败模式**：跨页表格 / 编号混用 / 页眉页脚混进正文 / 同一段被切两半

**验收**：抽 20 份文件人工看条款边界，边界准确率 ≥95%；抽 10 张表格，kv 还原正确率 ≥90%；每个条款都能在原文里按 span 取回同一段文字。

---

### C. 规则结构化（Applicability DSL）

**契约**
```
Clause → RuleSet[] | Unstructurable{
  rule_id, clause_id,
  applicable_if: [{field, op, value}]   合取，可带 unless
  grants: [benefit]                      落户/补贴/资格
  requires_docs: [材料]
  deadline, source_span, extracted_by, verified_by
}
```

**关键设计**
- **字段表先定，抽取后填**。约 20 个字段：city / audience / degree / school_tier / major / graduation_year / age_max / social_security_months / employer_qualified / contract_months …。先定表的好处是"抽取失败的字段"是显式的，而不是被模型悄悄编一个。
- **DSL 只支持合取 + unless，不支持任意逻辑**。够用，且可解释、可穷举、可测。
- **不可结构化的条款必须显式标记**。政策里满是"原则上""可适当放宽""由…认定"——这些落 `Unstructurable`，判定时直接进 unknown，**不允许 LLM 兜底拍板**。
- 规则带 `verified_by`：未人工核验的规则只做提示，不参与判定。这是"确定性"这句话能成立的前提。

**失败模式**：LLM 抽取时把"原则上"抽成硬条件 / 字段表覆盖不到的情况 / 抽取置信度高但错

**验收**：100 条金标条款，字段级准确率 ≥95%；模糊条款 100% 落入 Unstructurable；任一条规则能答出"它来自哪个 clause 的哪一句话"。

---

### D. 用户画像（Profile）

**契约**
```
Profile{ tenant_id, fields:{k:{value, source:self|doc, as_of}},
         missing:[k], snapshot_version }
```

**关键设计**
- **每个字段带来源和时点**。社保月数每月变、年龄每年变、毕业年份固定——判定必须带 `as_of`，答案里写"以 2026-11-11 的状态判定"。
- **缺失字段是一等公民**。缺失 → 进 `missing` → 触发澄清提问（最多 2 轮，每轮 ≤3 个问题），问不到就落 unknown。
- **画像版本化**：每次 run 存快照，事后能回答"当时判定用的什么信息"。
- 隐私：默认全本地模型（ollama），云端调用需显式开关，UI 上标注"本次请求发往云端"。

**失败模式**：用户随口说错 / 字段过期 / 澄清问太多把用户问跑了

**验收**：任一判定可回答"用了 profile 的哪几个字段、值、时点"；澄清轮次 ≤2。

---

### E. 判定（Judge）

**契约**
```
(Profile, RuleSet[]) → Judgement[]{
  clause_id, verdict, reason, failed_fields[], missing_fields[]
}
verdict ∈ {satisfied, unsatisfied, unknown, not_applicable}
```

**关键设计——四态，不是三态**

| 状态 | 含义 | 答案里怎么说 |
|---|---|---|
| `satisfied` | 适用且条件都满足 | 你能办，材料是… |
| `unsatisfied` | 适用但某条件明确不满足 | 你差 X（并给补足路径） |
| `unknown` | 适用，但某条件资料不足或条款模糊 | 判断不了，因为缺 X |
| `not_applicable` | 条款针对的不是你 | 这条不适用于你（不占篇幅） |

原来的三态把"你不符合"和"这条不针对你"混在一起，会让指标失真——用户是硕士、政策只招博士，这不是"不符合"，是"不适用"。

**冲突裁决**（同事项多份文件结论不同）：上位法 > 下位法；新 > 旧；特别 > 一般。**裁决结果必须显式呈现**，不能偷偷选一个。

**不变量**：`unknown → satisfied` 的转换次数恒为 0。这是整个系统的核心断言，也是评测里唯一"必须为 0"的指标。

**验收**：金标判定集上的四类混淆矩阵，重点看 `unknown` 是否被误报成 `satisfied`；冲突样本 100% 被识别并呈现。

### F. 组装与核验（Compose & Verify）

**契约**
```
Judgement[] + Clause[] → Answer{
  verdict_summary, evidence[], materials[], steps[],
  gaps[], as_of, corpus_version, coverage_statement
}
Claim{sentence_id, supports:[clause_id | judgement_id]}
```

**关键设计**
- **答案结构固定**，不自由发挥：结论 / 依据（原文 + 文号 + 链接）/ 材料 / 步骤 / 缺口 / 时效声明。
- **claim-level 核验**：组装出的每句话都要挂到某条 judgement 或某条 clause 上，挂不上的句子删掉。这是"无依据断言数 = 0"的实现方式。
- **材料必须来自 `requires_docs`**，步骤必须来自流程文档；LLM 不能自己编"带上身份证去街道办"。
- **拒答也要有证据**：没找到政策时，答案写"已检索 X 份文件 / Y 条条款，未发现；语料覆盖范围是…"，而不是干巴巴一句"我不知道"。

**失败模式**：引用错条款 / 断章取义 / 把 2024 版的材料清单套到 2026 版

**验收**：引用伪造率 0（机检：每条引用按 span 取回原文，与原句做字符级比对）；无依据断言数 0；核验失败后重写一次仍失败 → 直接降级为 unknown。

---

### G. 门控与动作（Gate & Act）

**契约**
```
Gate{ run_id, kind, payload, options, decision, decided_by }
Act : create_apply_task(task) --MCP--> 任务系统
```

**关键设计**
- **门控只在三种情况触发**：①要执行写操作 ②unknown 占比 >0.3 ③冲突未裁决。其余情况不打扰人——否则每轮都弹窗，用户会点"同意"点到麻木。
- **门控的对象是有副作用的一步**：写待办（材料清单 + 截止日 + 依据条款）到本地 mock 任务系统。这样"批准"才有真实含义：不批准就不落库。
- **动作走 MCP**（FastMCP 包一层 HTTP），幂等键 `run_id + action + payload_hash`。重放不产生第二条待办。
- 拒绝也留痕：拒绝的原因进审计，下次同类请求可以走快速通道。

**失败模式**：恢复后重复提交 / 批准了但写入失败 / 任务系统挂了

**验收**：批准 3 次只产生 1 条待办；拒绝 3 次 0 条；在 gate 处杀进程，重启 resume 后仍只有 1 条；任务系统 500 时重试不产生重复。

### H. 审计与评测（Audit & Eval）

**契约**
```
Run → Step[] → Span[]，每步带 input_hash/output_hash/耗时/corpus_version
EvalCase{ id, question, profile, gold_verdicts[], gold_clauses[], category, source }
```

**关键设计**
- **run tree 自存一份**（Postgres），Phoenix 只是可视化。观测平台挂了不影响回放——这是"trace 是产品不是装饰"的落地。
- **回放**：给定 run_id，用录制的 LLM 响应重跑，输出应逐字节一致（除时间戳）。
- **评测三层**：
  - 单元层：解析边界、规则抽取字段准确率、引用 span 命中率
  - 判定层：四类混淆矩阵（这才是本项目的主指标）
  - 系统层：端到端成功率、恢复幂等、拒绝合规、成本
- **消融**：baseline = 同检索 + 同组装，只把规则层换成"LLM 看条款自己判"；full = 规则 + 四态。差异才能归因到架构。
- 报告给 Wilson 区间，失败案例 100% 归类。

**验收**：同一 run_id 回放结果一致；消融两组只差一个变量；eval 全套 ≤30 分钟。

## 3. 状态机

```
normalize → load_profile → [clarify] ⇢ interrupt
          → route_policy → bind_rules → judge
          → detect_conflict → [gate_judgement] ⇢ interrupt
          → compose → verify ─(失败)→ compose（仅一次）
          → [gate_action] ⇢ interrupt → act → finalize
```

- 状态真源：**LangGraph checkpoint（PostgresSaver）是唯一真源**，`runs/steps` 是事件投影，不反向写。
- 幂等：每个节点写 `idempotency_keys(node, run_id, input_hash)`，重入直接返回上次结果。
- 中断点三个，全部 `interrupt()` + `Command(resume=...)`，恢复后从断点继续，不重跑已完成节点。

---

## 4. 证据模型：三层可回溯

```
Answer.claim  ──supports──▶  Judgement  ──from──▶  RuleSet  ──from──▶  Clause
                                                                        │
                                              char span / page / parser_version
                                                                        ▼
                                                                   原文（本地副本）
```

任何一层断了，上层结论就不许出现。**"可审计"不是加日志，是这条链每一段都有外键和偏移量。**

## 5. 项目怎么展开（六个里程碑，不是日程）

每个里程碑的完成标准是"**能演示 + 有数字 + 你能讲清**"，三者缺一不算完成。

| 里程碑 | 交付形态 | 验收数字 | 需要你判断的事 |
|---|---|---|---|
| **M0 可行性闸门** | 5 份真实文档跑通解析 | 扫描件比例、平均条款数、表格数 | 范围要不要缩 |
| **M1 单文档闭环** | 1 份文件 → 条款 → 检索 → 带引用回答 | 引用命中率 | 回答该长什么样 |
| **M2 判定闭环** | 规则 DSL + 四态 + 缺口提问 | 字段准确率、unknown 占比 | 什么算"说清了" |
| **M3 系统闭环** | 状态机 + checkpoint + 门控 + MCP 动作 | 恢复/幂等 3 项全过 | 门控阈值定多少 |
| **M4 多城分级** | 城市包 + 记分卡 + L1/L2/L3 + 2024 vs 2026 对比 | 每城级别、覆盖率、版本对比正确率 | 哪些城市停在 L1 |
| **M5 长期运行** | 变更事件 + 影响分析 + 漂移仪表盘 + smoke set | stale 规则自动标记率 | 核验节奏定多快 |
| **M6 证据** | 50 条金标 + 消融 + eval_report | 四类混淆矩阵 + Wilson 区间 | 哪些失败可接受 |
| **M7 交付** | ADR + 5 分钟录屏 + README | 无 | 讲哪三个决策 |

跨里程碑的四条主线（不是阶段，是同时推进的四个视角）：

- **数据线**：语料 → 条款 → 规则，每一步都要能回答"覆盖多少、缺多少"
- **判定线**：规则 → 四态 → 冲突，核心是"敢说不知道"
- **系统线**：状态 → 门控 → 动作 → 恢复，核心是"崩了不重复"
- **证据线**：金标 → 消融 → 报告，核心是"数字能归因"

## 6. 多城扩展：分级，而不是清单

"多城"不能理解成"再写三个 parser"——那会变成 N 份互相复制的代码，第三个月就没人敢动。
正确的做法是：**一个城市包（City Pack）= 配置 + 少量适配代码**，90% 的流程共用。

### 6.1 城市包契约

```
CityPack{
  city_code, name, level: L1|L2|L3,
  sources: [ {url, kind: list|detail|attachment, note} ],
  parser:  { list_selector, title_re, doc_no_re, date_re, clause_rules[] },
  taxonomy: [事项…],
  rule_ns: "sh.2026.",
  golden_cases: N
}
```

城市之间真正不同的只有五处：列表页结构、详情页选择器、附件挂在哪、文号格式、编号体系（`第X条` / `一、` / `（一）`）。
这五处全部配置化，抽取逻辑写一次。

### 6.2 接入记分卡（不达标就降级，不删）

| # | 检查项 | 阈值 |
|---|---|---|
| 1 | 源可达（≥3 个栏目） | 必须 |
| 2 | 附件发现率 | ≥80% |
| 3 | 条款边界抽检（20 份） | ≥95% |
| 4 | 可结构化条款占比 | ≥60% |
| 5 | 该城金标 | ≥8 条 |

过关 → 升 L2；某城过不了第 4 项，就停在 L1，**照样保留、照样在覆盖矩阵里显示为"仅检索"**。
这样"越多越好"才成立：广度靠 L1 铺，深度靠 L2/L3 收。

### 6.3 能力分级

| 级别 | 能做什么 | 不能做什么 | 验收 |
|---|---|---|---|
| **L1 检索** | 找到文件与条款原文、给引用 | 不做判定，答案只陈述"文件里写了什么" | 引用正确率 ≥95% |
| **L2 判定** | 四态判定、缺口提问、冲突呈现 | 不产生任何写操作 | 判定混淆矩阵达标 |
| **L3 动作** | 生成办理计划、落库待办（需批准） | — | 幂等/恢复 3 项全过 |

**答案里必须标注城市级别**（"杭州：仅检索模式，判定未覆盖"）。这是诚实，也是维护期的护城河——新增城市不会稀释已有城市的可信度。

### 6.4 跨城对比（副产品，但很值钱）

同一份画像在多个城市判定后，天然得到一张对比表：上海要 6 个月社保、杭州要 12 个月、成都要求不同。
这个功能不需要额外架构，**只需要判定层是结构化的**——正好是 L2 的产物。它也是"多城"从负担变成卖点的地方。

## 7. 长期维护：让系统活过第三个月

长期维护不是"以后再说"，它决定现在留什么接口。

### 7.1 变更是常态，所以要建模变更

每次 ingest 产出 `ChangeEvent{type: added|revised|repealed, doc_id, version_from, version_to, clause_diff[]}`。
**修订是唯一值得单独建模的事件**：政策改一个字，可能让 30 条规则失效。

### 7.2 变更影响分析（最容易被忽略的一环）

```
clause 变了 → 哪些 rule 指向它 → 标记 stale → 进核验队列 → 人工确认后才回到 effective
```

同时：**金标也会过期**。case 里 `gold_clause` 指向的条款变了，这条 case 自动标记"需复核"，不能继续拿来报数。
一个会自己发现"我的测试集过期了"的系统，比一个永远 95% 的系统可信。

### 7.3 漂移监控

每周看四个数：抓取失败率、覆盖率（事项维度）、判定分布（unknown 占比）、规则核验队列长度。
unknown 占比突然从 20% 涨到 45%，通常意味着某地政策改版而规则没跟上——这是最早的信号。

### 7.4 版本与迁移

- `parser_version`：改了分段规则，旧引用全部失效并重算，不能静默
- `corpus_version`：单调递增，任何答案都记录它
- schema 变更走 `make migrate`，**禁止手改库**
- 每次 ingest 后跑 smoke set（10 条），不通过不许发布

### 7.5 维护成本预算

**每周 30 分钟**：看漂移仪表盘 → 处理核验队列 → 跑一次 smoke。
如果维护超出这个量级，说明自动化不够，先补自动化再加城市。

## 8. 不做什么

- 不做实时政策订阅推送（那是产品，不是作品）
- 不做多轮自由对话（每轮都是独立 run，对话只用来澄清）
- 不做全国覆盖（3 城，超范围明确拒答）
- 不做 OCR（除非 M0 验出必须做）
- 不做前端框架（Jinja + HTMX，两个页面够）
- 不做 RAGAS 式的"回答质量打分"（不评文采，只评事实与行为）
